# 符号なしdot積でmat-vecを書き直す

**状態：同じランタイムで新カーネルだけを切り替えて3組ずつ交互に測り、decode tg32の平均は8.06から18.74 tok/s（2.33倍）、各回の2・3回目だけでは8.23から19.94 tok/s（2.42倍）になった。全logitの数値ゲートとtop1一致を通過。CPU主体の構成（llama-benchで約35 tok/s）にはまだ届かない。**

Pixel 11 ProのPowerVR C-Series CXTP-48-1536は、Vulkanの4×8ビットdot積のうち符号なし版だけを高速に実行する（`integerDotProduct4x8BitPackedUnsignedAccelerated`）。llama.cppの整数経路（MMVQ）は符号付き版を要求するため、この端末では使われず、量子化重みを1要素ずつfloatに戻す経路で動いていた。新しいシェーダーは重みと活性化を符号なしバイトに寄せてdot積を取り、ずれた分を整数で正確に補正する。対象はQ5_0・Q8_0・Q4_Kの1列mat-vec（decode）で、Qwen2.5-0.5Bの重みの大部分を占める。

[A/Bの全記録](../examples/inference/u8-mmvq-study/) · [カーネル単体の測定](../examples/kernels/study-20261104/) · [シェーダー](../guest/shaders/mul_mat_vecq_u8.comp) · [パッチ](../patches/llama-b11960-powervr-u8-mmvq.patch)

## 使う

llama.cpp b11960 / v0.8.0の未変更ソースから、既存の分割・完了待ちパッチに新パッチを重ねてビルドする。

    sh guest/build-inference-runtime.sh /absolute/fresh/llama.cpp-0.8.0 /absolute/stock-runtime /absolute/new-runtime --output-row-split --powervr-u8-mmvq
    ./pixel-lab run inference --runtime /absolute/new-runtime --gpu-layers 99 --split-output --u8-mmvq

`--u8-mmvq` は `GGML_VK_PWR_U8_MMVQ=1` を設定する。ランタイムの記録に新パッチがあること、Q8_0を含む68件のカーネル照合、全logitの照合（`--split-output` か `--sync-transfers` が必要）を要求し、さらにカーネル照合とモデル照合のログに新カーネルの選択記録（`ggml_vulkan: mul_mat_vecq_u8 selected for <型>`）があることを確かめる。パイプラインがないときは黙って従来のカーネルに戻るため、件数の形だけでは新カーネルが動いた証拠にならない。llama-benchは `-v` なしではライブラリのログを捨てるので、ベンチマークのログは記録するだけで条件にしない。環境変数がなければ従来どおりの経路で動く。

ビルド時にも同じ環境変数で68件を照合し、`kernel-check-u8.jsonl` と、Q4_K・Q5_0・Q8_0の選択記録を含む `kernel-check-u8.log` を残す（現在の版では、attentionスコアと4864行のmat-vecを含む102件と、Q6_Kを含む4種と形ごとの変種の選択記録。[decodeの続き](decode.md)・[形ごとの変種](matvec-variants.md)）。スクリプトは冒頭で `GGML_VK_*` の切り替えをすべて外し、照合ごとに必要なものだけを設定する。

### ビルド中のメモリ

標準ターミナルのアプリにはAndroidの `memory.high` 4 GiBがかかり、ゲストのページキャッシュも含めて数えられる。ターミナルが背面にあると、上限を超えた時点でアプリごとVMが終了する（2026-11-03に2回、logcatの `MemoryLimiter:AnonSwap`）。VM内で10 GB空いて見えても使えない。`ggml-vulkan.cpp` のO1コンパイルは単独で2.4 GiBを超えた。

ゲストのzram（zstd）を使い、ビルドをメモリ上限付きのユーザー単位で動かすと、背面でも完走した。Android側の最大は約2.5〜3.4 GiBだった。

    systemd-run --user --unit=spx-build --collect -p MemoryHigh=1900M -p MemoryMax=2100M -p MemorySwapMax=2500M \
      --setenv=CMAKE_PREFIX_PATH=/absolute/deps/usr sh -c 'sh guest/build-inference-runtime.sh ... > build.log 2>&1'

途中で止まった場合は、同じ引数に `--resume` を付ける。初回のパッチ適用時に、適用前の `ggml-vulkan.cpp` のハッシュとパッチ群のハッシュをソース直下の `.spiralpixcel-build` に記録する。再開時は記録の一致に加え、パッチが触るファイルの写しにパッチを逆順に当て戻し、記録した適用前のハッシュに戻ることを確かめてから続ける。完了したら記録に `completed=` を足し、同じ木での再開を断る。受領記録には `resumed_build` と各パッチのハッシュ（`patch_sha256`）を残す。

## カーネル単体の測定

`guest/kernel_bench.cpp` は、ggmlで量子化した乱数の重みに1つのシェーダーを繰り返し実行し、ggml自身の逆量子化から倍精度で求めた参照と照合する。重みの写しを回して前回のキャッシュを避ける。`guest/kernel-study.sh` で全項目を再実行でき、各行に特殊化定数を、`provenance.json` に参照側のlibggml-baseとスクリプト自身のハッシュを残す。

測り方に2つの落とし穴があった。

- ディスパッチの間にタイムスタンプを書くと、それだけで約100 µsかかる。llama.cppの `GGML_VK_PERF_LOGGER` は全ノードに書くため、小さい処理ほど大きく見える。RMS normは422 µsと出たが、単体ではバリア込みで約20 µsだった。
- アイドルの後、GPUのクロックが上がるまで約6 msかかる。短い列ほど遅く見える。

そこで、列の両端だけにタイムスタンプを書き、ウォームアップの後に、短い列とその5倍の列の差から1回分を求める。

## 何を変更したか

**シェーダー**（`mul_mat_vecq_u8.comp`）

- ワークグループは128レーン1サブグループ（必要サブグループサイズ128、full subgroups）。1行をTPR本のレーンで分担し、最後にクラスタ単位の `subgroupClusteredAdd` で足す。共有メモリとバリアは使わない。クラスタはサブグループ内の番号で決まるので、行の割り当ても `gl_SubgroupInvocationID` から求める（Vulkanはローカル番号との対応を保証しない）。Q5_0・Q8_0はTPR 4（1ワークグループ32行）、Q4_Kは64値ずつ32レーン（4行）。後で加えたQ6_Kも64値ずつ32レーン（4行、[decodeの続き](decode.md)）。
- 重みは32ビット単位で読む。Q5_0（22バイト）とQ8_0（34バイト）は偶数番目から2ブロックずつ読むと4バイト境界にそろい、奇数番目のブロックを半語ずらして組み立てる。この端末のggml-vulkanは4バイト境界までしか保証しないため、Q4_Kも32ビットで読む。
- 活性化はggml-vulkanの既存の `quantize_q8_1_x4`（128値ごとに144バイト）をそのまま使い、int8を `^ 0x80` で u = y + 128 にする。
- 補正式。Q5_0は x∈[0,31] が x−16 を表すので Σ(x−16)y = Σxu − 128Σx − 16(Σu − 4096)。Q8_0は x = w + 128 として Σwy = Σxu − 128(Σx + Σu) + 524288。Q4_Kは小ブロックごとに Σny = Σnu − 128Σn と Σy = Σu − 4096 を整数で求め、6ビットのscaleとminを掛ける。Σx・Σuもdot積で数える。整数部は桁あふれせず厳密。
- 行の繰り返しは全レーン同じ回数にした。レーンごとに異なる回数のループの中に `subgroupClusteredAdd` を置くと、約20%遅くなった。

**llama.cpp**（`llama-b11960-powervr-u8-mmvq.patch`）

このパッチは2026-11-04にQ6_Kを加えて改訂した（[decodeの続き](decode.md)、`9828dd27…`）。上の記録のr2は `df07510c…`、r3は `b6d4d7d7…`（コミット8b58939）の版で作った。以下は現在の版の説明で、Q6_Kに関わる部分は改訂で加わった。

- `GGML_VK_PWR_U8_MMVQ=1`、Imagination、デバイスとインスタンスのVulkan 1.3、`shaderIntegerDotProduct`、符号なしdot積の高速実行、clustered subgroup、サブグループサイズ制御とfull subgroupsがそろうときだけ有効にする。この端末はextension名 `VK_KHR_shader_integer_dot_product` を公開しないので、1.3のコア機能として機能構造体だけをつなぐ。
- 対象は `ggml_vk_mul_mat_vec_q_f16` の1列（ne11 = 1、バッチ1）で、Q5_0・Q8_0・Q4_K・Q6_K、Kが64の倍数、連続、128 MiBのstorage range以内、Q8を許す精度のとき。Q6_Kは210バイトのsuperblockの末尾にある `d` を語単位で読むため、テンソルの総バイト数が4の倍数のときだけ通す（そうでなければ従来のシェーダーに戻る）。活性化の量子化と、同じ入力を使う連続した行列積での再利用は既存のMMVQの仕組みに任せる。MUL_MAT_ADDのバイアス融合にも対応する。型ごとに初回の選択をログに書く。
- 生成器はQ5_0・Q8_0・Q4_K・Q6_Kの4種をコンパイルする。

**検査と道具**

- `check-mmv` にQ8_0を加え、56件から68件にした。新カーネルを通るのはn=1の16件（k = 768/896/1024、m = 128/896。q/oとk/vの形を含む。Q6_Kを加えた版では、k = 768/1024のQ6_Kの4件も通り20件）で、gate/upと出力層の大きな形はモデル照合が受け持つ。`inference.py` は両方の形を受け付け、`--u8-mmvq` では68件と選択記録を必須にし、VMの `boot_id` と起動からの秒数を受領記録に残す。
- `guest/kernel_bench.cpp`、`guest/kernel-study.sh`、`guest/shaders/bench/` の調査用シェーダー（読み出し、ALU、RMS norm、f16変換、浮動小数版Q5_0）を追加した。

変更は独立したレビュー（シェーダーの全分岐をPythonで再現する検証、ホスト統合、道具、証拠の4観点と、それぞれへの反証役）にかけ、指摘を直してからr3を作り直した。

## 効かなかったこと

- サブグループを32や64に縮めると、128より大きく遅かった。活性化を共有メモリに置いても遅くなった。どちらも、タイムスタンプの影響に気づく前の測り方での比較で、比の大きさは参考程度。→ 共有メモリが遅かったのは確保の大きさによるもので、必要な分だけにすると行の多い行列で速くなった（[形ごとの変種](matvec-variants.md)）。
- 浮動小数版では、`unpackUnorm4x8` で変換をまとめても191 µsから161 µs（約16%）までしか縮まなかった。FP16はFP32より遅い。
- Q4_Kを256値のsuperblock単位でレーンに配ると、既存のQ4_Kカーネルと同程度で、64値単位に分けて1.2倍になった。
- RMS normは単体ではほぼディスパッチの固定費で、サブグループ化しても変わらない。

## 残っていること

新カーネルでの1トークンは約52 ms、CPUは約22 ms。

- Q6_Kのdown（201 µs×12）とattentionのf16 mat-vecは書き換えていない。→ [decodeの続き](decode.md)で、attentionスコアの専用シェーダーとQ6_Kの符号なしカーネルを加えた。
- 1トークンにつき約417回のディスパッチがあり（性能ロガーの回数から）、バリア込みで1回13 µs以上かかる。新カーネルは活性化の量子化で85回増やした（各層のq/k/v、o、gate/up、Q4_Kの層のdown、出力層で1回ずつ）。→ ggmlのバリアは転送ステージを含むため実際には1回20〜54 µsかかっていた。[decodeの続き](decode.md)を参照。
- 小さい形（128行）は固定費が支配的。
- 全logitの照合は1位置だけ。複数のプロンプトでの全位置の比較や、KLなどの分布の比較はしていない。
- 1.5Bなど他のモデル、長いcontext、持続負荷、他の端末は未評価。
