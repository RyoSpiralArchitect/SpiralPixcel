# decodeの残り時間を削る：バリア・メモリ配置・attention

**状態：最終版のr6ランタイムで切り替えだけを変えて3組ずつ交互に測り、decode tg32の平均は18.89から28.56 tok/s（1.51倍）、各回の2・3回目だけでは19.97から30.80 tok/s（1.54倍）になった。全logitは切り替えの有無でバイト単位まで同じ。1024トークンの文脈の後では12.5から19.7 tok/s（1.58倍、r4でのゲートなしの補足測定）。CPU主体の構成（約35 tok/s）にはまだ届かない。**

符号なしdot積のmat-vec（[前回](kernels.md)）の後も、GPUでのdecodeは1トークン約50 msかかり、CPU主体の構成より遅かった。今回は、その50 msの内訳をホストとGPUの両側から測り直した。ホスト側の待ちは大半がGPUの実行待ちで、GPU時間の多くは計算ではなく、バリア、メモリの置き場所、attentionの小さいワークグループに使われていた。変更は3つの切り替えにまとめた。どれも既定では無効。

- `GGML_VK_PWR_ATTN=1`：1トークンのattentionスコア（K×q、GQA）を、1ワークグループで16位置ずつ計算する専用シェーダー（`mul_mat_vec_p021_pvr.comp`）。
- `GGML_VK_PWR_BARRIER=1`：計算どうしの依存に、転送ステージを含まない安いバリアを使う。転送コマンドの前には専用のバリアを置く。
- `GGML_VK_PREFER_DEVICE_LOCAL=1`：UMAでもデバイス用バッファをdevice-localのメモリ型に置く。

あわせて、符号なしdot積のmat-vecにQ6_Kを加えた（`GGML_VK_PWR_U8_MMVQ=1` に含まれる）。

[A/Bの全記録](../examples/inference/decode-study/) · [調査の測定](../examples/kernels/decode-20261104/) · [パッチ](../patches/llama-b11960-powervr-decode.patch) · [測定用の道具](../guest/probes/)

## 使う

    sh guest/build-inference-runtime.sh /absolute/fresh/llama.cpp-0.8.0 /absolute/stock-runtime /absolute/new-runtime --output-row-split --powervr-u8-mmvq --powervr-decode
    ./pixel-lab run inference --runtime /absolute/new-runtime --gpu-layers 99 --split-output --u8-mmvq --powervr-decode

`--powervr-decode` は上の3つの環境変数を設定する。分割出力の全logit照合（`--split-output`）が必要で、ランタイムの記録に `powervr_decode` があること、76件のカーネル照合（attentionスコアの8件を含む）、カーネル照合とモデル照合のログに `ggml_vulkan: mul_mat_vec_p021_pvr selected` があることを確かめる。モデル照合は33トークンを16・16・1トークンに分けて計算するので、最後の1トークンで新しいシェーダーを通る。

ビルドの `--powervr-decode` は `--output-row-split` と `--powervr-u8-mmvq` を必要とする（両者の変更の上に当たる）。ビルド時に、3つの切り替えと符号なしmat-vecをすべて有効にして、転送27件、カーネル76件、大行列2件をもう一度照合し、`readback-check-decode.jsonl`・`kernel-check-decode.jsonl`・`large-check-decode.jsonl` と選択記録を残す。

## どこに時間がかかっていたか

### ホスト側：待っているのはほぼGPU

`llama-bench`（1 CPUスレッド）を `LD_PRELOAD` の小さなシム（[`guest/probes/vkshim.c`](../guest/probes/vkshim.c)）で包み、Vulkan呼び出しの回数と時間を数えた。32トークンと160トークンの差を128で割り、1トークンあたりにした（[記録](../examples/kernels/decode-20261104/host/)）。

- 1トークン約44 msのうち33 msが `vkQueueSubmit`（約11回）の中、9 msが最後の `vkQueueWaitIdle`、2 msが入力アップロードのfence待ちだった。502回のディスパッチの記録そのものは0.15 ms。
- ゲストのメインスレッドは常に1コアを使い切っていた（user約7 ms、sys約41 ms、[記録](../examples/kernels/decode-20261104/host/cpu-time.json)）。Android側の `/proc` を読むと、VMの中でGPUの命令を処理するスレッド（ゲストのプロセス名が付く）は1トークン約35 ms（user 4.1・sys 30.5 ms、[記録](../examples/kernels/decode-20261104/host/host-threads.json)）を使っていた。待ちの間も空回りするので、CPU時間だけでは原因がGPUかホストか決まらない。
- 各コマンドバッファの両端にタイムスタンプを書くと、GPUの実行は1トークン約41.6 msだった。この計測の壁時計は約51 ms（タイムスタンプの分を含む）。バッチの間の空きは大半が30〜50 µsで、トークンの切れ目の前後だけ合わせて約8 ms空いていた。GPUが動いていない時間はこの切れ目にほぼ集まる。

生のVulkanで同じ端末を測ると（[`submit_probe.c`](../guest/probes/submit_probe.c)）、空に近い1回の投入は往復約0.18 ms、続けて投入すると1回あたり50〜250 µs。llama.cppのプロセスでは、入力アップロードの空に近い投入が往復約2.1 msかかった。

### 空の投入に付けたfenceは早く立つ

`vkQueueSubmit(queue, 0, NULL, fence)` のfenceは、6.8 ms分の仕事が先に投入されていても約0.15 msで立った。仕事に付けたfenceと `vkQueueWaitIdle` は正しく約7.05 ms待った。ggml-vulkanの同期は空の投入にfenceを付けるので、この端末で読み出しが古い値になった原因はこれと考えられる（[完了待ちの経緯](readback.md)）。キュー完了待ち（`GGML_VK_WAIT_IDLE=1`）は正しい回避策で、仕事に付けたfenceと同じ時間で済む。

### バリアの費用は宛先ステージで決まる

1つのコマンドバッファの中で小さいディスパッチを並べ、間に置くバリアだけを変えた（[`dispatch_probe.c`](../guest/probes/dispatch_probe.c)、1ワークグループのディスパッチ1回あたり）。

| ディスパッチの後 | µs |
| --- | ---: |
| バリアなし | 0.4 |
| 実行依存だけ（メモリバリアなし） | 0.1 |
| 書いた範囲だけのバッファバリア | 5.3 |
| synchronization2、計算ステージ、storage書き→読み | 5.4〜10 |
| compute→computeのメモリバリア | 7〜15 |
| compute＋transfer → compute | 5.3 |
| compute → compute＋transfer | 22 |
| ggmlのバリア（両側compute＋transfer、4種のアクセス） | 21〜54 |

アクセスの種類はほとんど影響せず、宛先にtransferステージを入れると高くなる。ggml-vulkanの `ggml_vk_sync_buffers` は、計算どうしの依存にもこの高いバリアを使い、1トークンで約380回置く。パイプラインや記述子セットの切り替えは1回0〜3 µs、タイムスタンプはこのプローブで1回約64 µsだった。

### メモリの置き場所

ggml-vulkanは統合GPU（UMA）では、デバイス用バッファをまずホストから見えるcoherentなメモリ型（この端末の型2：DEVICE_LOCAL・HOST_VISIBLE・HOST_COHERENT・HOST_CACHED）に置く。約374 MiBの重みはこの型に入りきらず型0（DEVICE_LOCALのみ）に落ちるが、計算バッファ（この160トークンの測定で約27 MiB）、KVキャッシュ、出力などは型2に入る。シムでメモリ型の表示から型2のDEVICE_LOCALを外すと、これらは型0に移り、GPU時間が約4.5 ms減った。新attentionと安いバリアを有効にした状態でdevice-localを足すと、1トークンの壁時計とGPU時間の差（GPUが動いていない時間）も約7.5〜10 msから約4.5 msに縮んだ（[記録](../examples/kernels/decode-20261104/graph/dl1-summary.jsonl)）。

型2のメモリを持つだけでは往復は遅くならなかった（生Vulkanで16〜64 MiBを確保して試した）。何がVM越しの投入を遅くしていたかは特定していない。

### 演算ごとの費用

演算を飛ばす方法（`GGML_VK_SKIP_OPS`）では、その演算への依存も消えて後ろの仕事が前に重なるため、節約量が足し合わない（全部の小演算を飛ばすと12.6 ms、個別の和は20.9 ms）。そこで逆に、指定した種類の演算を2回記録して（間にバリア）、増えた時間を測った（`GGML_VK_DUP_OPS`）。測るたびに直前に基準を測り、組で差を取った。device-local・安いバリア・新attentionを有効にした状態（基準GPU 28.2〜29.5 ms/トークン）：

| 2回にした演算 | 増えたGPU時間（ms/トークン） | 1トークンの回数 | 1回あたり |
| --- | ---: | ---: | ---: |
| Q5_0 mat-vec（q/k/v/o/gate/up） | 8.15 | 132 | 62 µs |
| attentionのf16 mat-vec（スコアと重み付き和） | 4.92 | 48 | 102 µs |
| Q6_K down（ggmlのシェーダー） | 4.21 | 12 | 351 µs |
| Q8_0（出力層と一部のv） | 2.94 | 15 | – |
| RMS norm | 2.00 | 49 | 41 µs |
| CONT（attention出力の並べ替え） | 1.91 | 24 | 80 µs |
| SET_ROWS | 0.75 | 24 | 31 µs |
| ROPE | 0.55 | 48 | 11 µs |
| Q4_K down（符号なしdot積） | 0.68 | 12 | 57 µs |
| SOFT_MAX、GLU | 約0 | 各24 | – |

2回目の行列積は重みがキャッシュに残るので、帯域で決まるカーネルでは小さめに出る（Q4_Kの57 µsは単体測定の約110 µsより短い）。Q6_Kの351 µsは置き換えても縮まなかった（下）。

## 何を変更したか

**attentionスコア**（`mul_mat_vec_p021_pvr.comp`）

元の `mul_mat_vec_p021.comp` は、KVの1位置ごとに128レーンのワークグループを1つ使い、64次元の内積を64レーンで1回ずつのFMAとサブグループ加算で求める。256位置×KVヘッド2で512ワークグループになり、この端末では1つ約0.5 µsかかる。新しいシェーダーは、1位置を8レーンで分担し（f16vec4を2回読む）、1ワークグループで16位置を計算する。GQAのクエリ（7ヘッド）は共有メモリに一度だけ置き、`subgroupClusteredAdd` で8レーンを足す。

単体の測定（[記録](../examples/kernels/decode-20261104/attention/)）では、出力はすべて書かれ、倍精度の参照に対するNMSEは元のシェーダーと同じ約5e-15（ビットは約7割の出力で最下位付近が異なる）。

| KV位置×次元×KVヘッド×GQA | 元 | 新 |
| --- | ---: | ---: |
| 33×64×2×7 | 40〜111 µs | 21 µs |
| 256×64×2×7 | 244 µs | 48 µs |
| 1024×64×2×7 | 791 µs | 121 µs |
| 4096×64×2×7 | 3085 µs | 403 µs |
| 256×128×4×2 | 207 µs | 42 µs |
| 100×64×14×1 | 274 µs | 43 µs |

元のシェーダーの33位置は回によって40〜150 µsと揺れた（[記録](../examples/kernels/decode-20261104/attention/)の2つのファイル）。1ワークグループで32〜128位置を順に処理する形も試したが、どのcontext長でも16位置が最も速かった。全logitはビット単位で変わらなかった。次の行列積の前に活性化を8ビットへ量子化するため、内積の最下位ビットの違いがそこで消える。

**バリア**

`ggml_vk_sync_buffers` を、元をcompute＋transfer、宛先をcomputeだけにしたバリアに替えた（アクセスは書き込み→読み書き）。転送コマンド（コピー・塗りつぶし）を記録する12か所では、その直前に `ggml_vk_sync_before_transfer`（元compute＋transfer、宛先transfer）を置く。転送が後に続く依存はこの専用バリアで、計算が後に続く依存は安いバリアで覆われる。切り替えはキューに記録するので、ホストのコンテキストを持たない転送用の同期でも同じ規則になる。転送専用キューは元のまま。

**メモリ配置**

`ggml_vk_create_buffer_device` で、UMAでもまずdevice-localを、だめならホストから見えるcoherentな型を選ぶ。アップロードと読み出しは既存のステージング経路を通る。

**ピン留めメモリへの読み出し**

r4の後、レビューでの修正（検査と引数の確認だけで、パッチは同じ）を入れて作り直したr5で同じA/Bを回すと、6回のうちdecodeの切り替えonの1回が転送の照合で止まった。Vulkanのホストバッファ（ピン留めメモリ）への64バイトの読み出し（`async_api_vulkan_host`）で、3回の試行のうち2回、64バイトすべてが0だった。照合は読み出しの前にこのバッファを0で埋めるので、GPUのコピーの結果がCPUから見えていなかった。r5で `check-readback` を切り替えの組み合わせごとに20回ずつ繰り返すと、失敗した回数は切り替えなし0、安いバリアだけ0、device-localだけ3、3つすべて3だった（[記録](../examples/kernels/decode-20261104/readback/)）。失敗はどれもピン留めメモリへの読み出しの2回目か3回目の試行で、64バイト・4 KiB・1 MiBのどの大きさでも起きた。64バイトの件では全体が、4 KiBと1 MiBの件では一部（64〜383バイト）が、読み出しの前に書いた0のままだった。r4の6回とビルド時の照合が通ったのは、この頻度なら偶然でもおかしくない。

device-localにすると読み出し元がホストから見えなくなり、`ggml_vk_buffer_read_2d` はステージングの経路に入る。読み出し先がピン留めメモリなら、GPUがそこへ直接コピーし、CPUの `memcpy` は通らない。既存の変更（[大きな出力行列](large-output.md)）は、待った後にステージング領域だけを無効化していた。パッチでは、読み出し先がピン留めメモリのときはその領域にも `vkInvalidateMappedMemoryRanges` を呼ぶ（分割出力のときだけ、既存の無効化と同じ条件）。分割出力では非同期の転送を切る（`GGML_VK_DISABLE_ASYNC=1`）ので、読み出しはすべてこの同期の経路を通る。実験用のランタイムと最終版のr6で4つの組み合わせを各30回繰り返し、どちらも1回も失敗しなかった。

照合用のバッファだけの問題ではない。llama.cppはlogitsの出力先にも出力層のデバイスのホストバッファを使うので（実行の記録では `Vulkan_Host output buffer size = 0.58 MiB`）、device-localにすると毎トークンのlogitsもこの経路で読む。修正前のr4でも全logitの照合と64トークンの生成は一致していたが、速度測定の中で読んだlogitsは照合していない。

**Q6_K**（`mul_mat_vecq_u8.comp`）

Q6_Kの値は下位4ビットと上位2ビットを合わせた0〜63なので、そのまま符号なしバイトとしてdot積に使える。16値ごとのscaleで Σ(q−32)y = Σqu − 128Σq − 32(Σu − 2048) を整数で求める。superblockは210バイトで1つおきに2バイトずれるため、9語の読み出しから8語を組み立てる。単体では165〜169 µs（ggml 198〜202 µs）で、NMSEは約4.8e-15。グラフの中では、Q6_Kのない同じ構成との交互測定でGPU時間の差が0〜1.2 ms（平均0.6 ms）で、雑音と区別できない。全logitのNMSEは0.002615から0.002360になった。

**検査と道具**

- `check-mmv` に、llama.cppと同じ置換（0, 2, 1, 3）をしたf16のKとクエリのattentionスコア8件を加えた（次元64/80/128、KVヘッド2〜14、GQA 1〜8、33〜1000位置）。KVヘッドが1つだと置換が形だけになり、ggmlは置換用の経路を通らないので、どの件もKVヘッドを2つ以上にした。68件から76件。
- `inference.py` と `pixel-lab` に `--powervr-decode` を加え、76件と選択記録を必須にした。ビルドの受領記録に `powervr_decode` と、符号なしmat-vecの対象型（`powervr_u8_mmvq_types`）を残す。
- [`guest/probes/`](../guest/probes/)：Vulkan呼び出しの計時とコマンドバッファ単位のGPUタイムスタンプを取るシム、投入とバリアの測定、attentionスコアの単体照合。

## 効かなかったこと

- softmaxの縮約をサブグループ演算に替えた版は速くならず（GPU時間で差なし）、全logitのNMSEが0.002615から0.002786に動いたので外した。
- 1トークンのグラフを1回で投入すると、GPU時間が約6 ms増えた（約10回に分ける既定より遅い）。
- Q6_K・Q4_Kの符号なしカーネルで、1行のレーン数（8・16・32）と1グループの行数（1・2・4）を変えても、既定（32レーン・1行）より速くならなかった。どちらも読み出し上限の4割程度で、待ち時間で決まっている。

## 測り方

- 速度は同じ時間帯に交互に測った組だけを比べた。GPUのクロックは `/sys/class/devfreq/34f00000.gpu0/cur_freq` で読め、decode中はほぼ1286 MHzだったが、連続測定の途中でGPU時間が15%遅くなる時間帯があった。
- 全logitの照合は、ビット単位の一致も確かめた。バリアとメモリ配置だけを変えたランタイムでは、何度測ってもr3の候補ベクトル（`511616a0…`）と一致した。
- r6はr5と、decodeパッチに加えた部分だけが違う。ビルドの場所の文字列とbuild-idを除くと、`libggml-vulkan.so` 以外のライブラリと道具はr5とバイト単位で同じだった。
- 実験用のランタイムは、上の切り替えに加えて、演算を飛ばす・2回にする・1回で投入するための測定用の切り替えを持つ（最終のパッチには入れていない）。[パッチと順序](../examples/kernels/decode-20261104/provenance.json)。

## 残っていること

- GPU時間（1トークン約28 ms）の最大はQ5_0のmat-vec（約8 ms）。符号なしカーネルは読み出し上限の4割程度で、詰めるには重みの並べ替えなど配置からの変更が要る。
- 2回にした測定で、attentionのf16 mat-vec（新しいスコアと重み付き和の合計）は約4.9 ms、RMS normは約2 ms、CONTは約1.9 ms。スコアは単体で1回約48 µs（24回で約1.2 ms）なので、残りの大半は重み付き和と考えられるが、分けては測っていない。CONTは重み付き和の出力を並べ替えるだけで、出力先を直接書けば消せる。
- トークンの間のホスト側の空き（数ms）。入力の同期アップロードと、コマンドプールのリセットがVMの往復になっている。
- 全logitの照合は1位置だけ。長いcontext、他のモデル、持続負荷は未評価。
